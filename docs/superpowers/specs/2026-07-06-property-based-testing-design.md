# Design: property-based testing for @effect-postcodes/client

## Context

The current test suite has 6 example-based tests across three files. This spec
adds property-based tests using `FastCheck` from `effect/testing` (no extra
dependency — fast-check is already a transitive dep of `effect`). Two new
`.property.test.ts` files cover orthogonal concerns: one purely hermetic
(schema-level), one behavioral (client against the mock server).

## Public API change: export Schema values, not just types

`src/index.ts` currently re-exports domain types as `export type { PostcodeResult, ... }`.
This means consumers cannot call `Schema.toArbitrary(PostcodeResult)` from the
package because the Schema value is stripped at compile time. Changing to
`export { PostcodeResult, OutcodeResult, PlaceResult, BulkLookupItem, ErrorEnvelope }`
(value exports that also carry the type) enables arbitrary derivation from the
public API — a genuine improvement for any consumer doing property-based testing.
The generated schemas are already bundled into `dist/` by tsdown; this just
makes them accessible as named exports.

## File 1: `test/schema.property.test.ts`

**Purpose:** Pure schema invariants — no HTTP, no mock server, deterministic
and fast. Uses `Schema.toArbitrary` to derive arbitraries from the package's own
schemas and verifies structural invariants that must hold for all valid values.

**Imports:**
```ts
import { describe, test } from "bun:test"
import { FastCheck } from "effect/testing"
import { Schema } from "effect"
import {
  PostcodeResult, OutcodeResult, PlaceResult,
  BulkLookupItem, ErrorEnvelope
} from "../src/index.ts"
```

**Properties:**

1. **PostcodeResult region is always `string | null`** — never `undefined`,
   never any other type. Generated shapes always satisfy the fixed nullable
   contract, providing regression coverage for the EH25 9NJ bug class.

2. **PostcodeResult decode is total** — every value generated by
   `Schema.toArbitrary(PostcodeResult)` is also decodeable by `PostcodeResult`
   (no self-inconsistency between the arbitrary and the decoder). Uses
   `Schema.decodeUnknownSync(PostcodeResult)` on each generated value.

3. **BulkLookupItem result is `PostcodeResult | null`, never undefined** —
   generated items always have a result field that is either a full postcode
   object or exactly `null`.

4. **ErrorEnvelope status is always `404`** — generated envelopes always carry
   the literal `404` status code, not any other number.

5. **Path encoding is an identity under roundtrip** — for any string `s`,
   `decodeURIComponent(encodeURIComponent(s)) === s`. Pure fast-check property
   with `FastCheck.string()`, no Effect needed.

**Pattern:** `FastCheck.assert(FastCheck.property(arbitrary, predicate))` — fully
synchronous, wraps in bun:test's `test()`.

## File 2: `test/client.property.test.ts`

**Purpose:** Behavioral invariants across the client → mock server boundary.
Verifies that the client's public API maintains structural guarantees for
arbitrary inputs. Uses `FastCheck.asyncProperty` since each predicate runs an
Effect through the mock server.

**Imports:** same mock server helpers as `test/contract.test.ts`, plus
`FastCheck` from `effect/testing`, `Effect`, `Layer`, `FetchHttpClient`,
`PostcodesClient`, `isApiNotFoundError` from `"../src/index.ts"`.

**Properties:**

1. **Error type invariant for `lookupPostcode`** — for any arbitrary string `s`
   as the postcode argument, the outcome is either `right(PostcodeResult)` or
   `left(ApiNotFoundError)`. It is NEVER `left(SchemaError)`. A `SchemaError`
   would mean the path encoding failed and the request hit the wrong route
   (returning a response whose shape doesn't match `OutcodeResult` or
   `PlaceResult` for example), so this property covers path-encoding correctness
   indirectly.

2. **Bulk lookup length invariant** — for any non-empty array of strings
   (1–10 items), `bulkLookupPostcodes(arr)` returns an array whose length equals
   `arr.length`. The mock always returns two fixture items regardless of input,
   so this property is verified against a hardcoded bulk response — but the
   property is stated as a general invariant the client must always uphold.

3. **Service completeness** — `PostcodesClient.Default` always provides an
   object with exactly the four required methods: `lookupPostcode`,
   `bulkLookupPostcodes`, `findOutcode`, `findPlace`. Uses `FastCheck.constant`
   (a single "arbitrary" that always yields the same value) to express this as a
   property rather than an example-based test.

**Pattern:** `await FastCheck.assert(FastCheck.asyncProperty(arb, async (value) => { ... }))`,
wrapped in bun:test's `async test()`. Limit to `{ numRuns: 25 }` for network
properties to keep the suite fast.

**Layer setup** (shared across all client properties):
```ts
const clientLayer = PostcodesClient.layer({ baseUrl }).pipe(
  Layer.provide(FetchHttpClient.layer)
)
```

## `package.json` test script

Add both new files:
```json
"test": "bun test test/contract.test.ts test/fullClient.elysia.test.ts test/rateLimiting.test.ts test/schema.property.test.ts test/client.property.test.ts"
```

## Out of scope

- Property tests for `findOutcode` / `findPlace` behavioral invariants (low
  value: same invariant as `lookupPostcode`, already covered by property 1)
- Shrinking / custom shrinkers (fast-check's built-in shrinkers are sufficient)
- Stateful property testing (machine model)
- Changes to `generated/` files
